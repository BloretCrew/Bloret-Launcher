Bloret Launcher Passport OAuth PKCE 迁移计划

目标：将 Launcher 的 Passport 登录从旧的自定义 app_secret/app/verify 流程迁移到 Passport 已支持的标准 OAuth 2.0 Authorization Code + PKCE（S256）流程。

范围

  • Launcher 客户端：/data/Bloret-Launcher。
  • Passport 服务端只做只读协议确认；除非发现标准 PKCE 缺口，不直接修改生产 Passport。
  • 不处理 sign/root.pvk，不提交任何凭据。

目标流程

Launcher 生成 code_verifier/state
→ 打开 Passport /oauth/authorize?client_id=...&redirect_uri=...&response_type=code&code_challenge=...&code_challenge_method=S256
→ 用户在 Passport 登录并授权
→ Passport 回调本地 redirect_uri，带 code/state
→ Launcher 校验 state
→ POST Passport /oauth/token（code、redirect_uri、code_verifier）
→ GET /oauth/userinfo（Bearer access_token）
→ 保存短期 token/用户资料并完成同步

必须完成

  1. 盘点当前 Launcher OAuth 回调、配置字段、登录状态保存和 Minecraft 账号同步调用链。
  2. 移除 Launcher 生产代码中的静态 app_secret 和旧 /app/verify 依赖。
  3. 实现 PKCE：高熵 verifier、S256 challenge、不可预测 state、回调一次性消费和超时。
  4. redirect_uri 必须是本机 loopback 随机端口或项目现有安全回调地址，严格校验来源和 state；不得把 verifier/token 放 URL。
  5. 使用 Passport 标准 /oauth/authorize、/oauth/token、/oauth/userinfo。
  6. token 只存本地安全配置，不写日志；用户取消、拒绝、code 缺失、state 不匹配、code 过期、PKCE 失败和 HTTP 非 2xx 都显示明确错误。
  7. 兼容现有用户配置：不要破坏已有用户资料；旧 token 失效时要求重新授权，不回退到明文 app_secret。
  8. 确认 Passport OAuth App 的 client_id、redirect_uri 和 PKCE 配置来自安全配置/服务端注册信息，不在客户端放 client_secret。

测试

  • 先增加失败回归测试，再实现。
  • 覆盖 verifier/challenge、state、防重放、回调校验、token 换取、userinfo、拒绝/过期/非 HTTPS、凭据不进 URL/日志。
  • 使用本地 mock Passport 或隔离临时服务，不访问生产 Passport 和生产数据库。
  • 运行 Python 编译、项目现有测试和新增 OAuth 测试。
  • 如果当前 Linux 无 GUI，只做协议/服务测试，并明确 Windows GUI 未验证。

验收

  • 源码扫描确认生产代码不再包含旧 Passport app_secret。
  • 源码扫描确认远程 OAuth 不允许 HTTPS 降级到 HTTP。
  • 隔离 mock 完成完整 PKCE 流程。
  • 真实 Passport 只做只读 well-known/endpoint 确认，不登录、不修改生产。
  • 只 commit 不 push，输出协议证据、测试结果和未验证项。
